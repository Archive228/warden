# Project: warden — agentic launch-vetting tool
# Last updated: 2026-09-06 by session 4 (repo-authenticity fingerprint)

## What's done
- On-chain Pons v2 reader [feature_list.json index: 0] — unchanged this session.
- Repo/social authenticity fingerprint [feature_list.json index: 1] — passes:true,
  verified against real ground truth, not synthetic examples. `warden vet-repo
  <owner>/<repo>` reports: account-created-at vs the account's oldest visible repo
  (dormancyGapDays), fork creation timestamps and the largest cluster within a
  30-minute sliding window, star COUNT only (timing deliberately unavailable, see
  below), and text-mention scanning of the README + owner bio split into two
  separately-reported buckets: contractAddressMentions (raw 0x... matches — weak
  signal alone) and tickerMentions ($XXXX-style — much sharper signal).

  Verified two ways, both against real repos, not mocks:
  1. Positive control: github.com/Phosphenq/bodkin — the exact repo this whole
     project's "Why" is about. Ran `vet-repo` against it live and got
     dormancyGapDays=2487 (matches the known ~6.8-year-old dormant account),
     forkBurst={count:6, windowMinutes:30, first/last exactly 19m7s apart} (matches
     the originally-researched "6 forks in a 19-minute window" finding to the
     second), tickerMentions=[$BODKIN in readme, $BODKIN in bio] (matches). The tool
     independently reproduces, from scratch, a red-flag profile that previously took
     a full research pass to find by hand.
  2. Negative control: github.com/ponsdotdev/ponsfamily (the real, legitimate Pons
     contracts repo). This is what caught a real design flaw before it shipped: its
     README legitimately mentions 4 contract addresses (V1/V2 factory addresses,
     real technical documentation) — a naive single "token mention" signal would
     have flagged this as shilling. Splitting into contractAddressMentions (weak,
     common in any protocol-integration repo) vs tickerMentions (strong, near-zero
     false-positive rate expected) fixed it: ponsfamily shows 4 contract-address
     mentions and 0 ticker mentions, correctly not flagged.

  Both are now automated tests (src/repo/fingerprint.test.ts) that skip cleanly
  (Deno.test ignore) rather than failing confusingly when GITHUB_TOKEN isn't set —
  unauthenticated GitHub API calls hit a much lower rate limit and 403'd outright on
  one endpoint during this session's testing (reproduced live: unauthenticated
  GET /users/ponsdotdev -> 403; same call with a token -> 200). Total test count
  now 7/7 passing (3 chain + 2 fingerprint + 2 retry), all against live services,
  no mocks anywhere in this codebase so far.

## Notes for the next session
Runtime is Deno. `deno task start scan <address>`, `deno task start vet-repo
<owner>/<repo>`, `deno task test`. Tests that hit the GitHub API need
GITHUB_TOKEN in the environment or they skip (not fail) — `gh auth token` works
fine as a source if `gh` is authenticated on the machine, same as this session did.

Two src/repo/ files exist now: github.ts (thin authenticated-fetch wrapper,
falls back to unauthenticated if GITHUB_TOKEN unset) and fingerprint.ts (the
actual vetRepo logic). Both are new surface area for the next session to be aware
of alongside src/chain/.

Standing lesson from session 3, reapplied successfully this session: don't ship a
single blended "risk signal" out of two things with very different reliability —
splitting contractAddressMentions from tickerMentions here is the direct
application of the same principle as splitting DevBuy into
available:true/false instead of a bare number that could silently mean either
"zero" or "couldn't check." Look for this pattern before merging any two facts
into one field for the rest of this project.

Everything from session 3's notes about the on-chain side still holds (Robinhood
Chain id 4663, Pons v2 factory/locker addresses, the snipe-tax bytecode-vs-public-
repo discrepancy, holder-concentration denominator fix, retry/backoff wrapping) —
not repeated here, read the git log (session 3's commit message has the full
rationale) rather than trusting this file alone if it's been a while.

Do not commit a real .env. GITHUB_TOKEN, same as the wallet key, only ever read
from environment at runtime.
