## What's next (recommended)
- Repo/social authenticity fingerprint [feature_list.json index: 1]
  Reason: second-most foundational signal, and the one the agent-judge feature needs
  alongside the on-chain read to write a real verdict.
  IMPORTANT gotcha already found by research (do not re-derive, just apply): GitHub
  restricted the stargazers-listing endpoint to admin/collaborators as of ~July 2026.
  REST /repos/{o}/{r}/stargazers now 404s for any third-party repo. GraphQL
  `stargazers { edges { starredAt } }` does NOT error on a third-party repo — it
  silently returns an EMPTY edges array even when stargazerCount confirms real stars
  exist. A naive implementation would misread "access denied" as "zero stars, real
  red flag" — this must be handled explicitly (report "star timing unavailable",
  never treat empty as a genuine signal). Fork timing (`GET /repos/{o}/{r}/forks`,
  `created_at` per fork) is NOT restricted and works fine — lean on that instead.

Verified Pons v2 / Robinhood Chain facts now baked into the code (src/chain/abi/*,
src/chain/robinhoodChain.ts) — don't re-derive these, they're sourced and correct
as of 2026-09-05:
- Robinhood Chain id 4663, RPC https://rpc.mainnet.chain.robinhood.com (verified live
  via eth_chainId). Public RPC is rate-limited per Robinhood's own docs — fine for
  this tool's read volume, would need Alchemy/QuickNode for anything higher-frequency.
- Pons V2 factory 0x7eD598BcEf8bd9Edd8C97A195C6d13f40801EC7e and launch locker
  0x267444D099b10fB5Ed7c3Cc7B7c767AdcA574952 — both verified on Blockscout, ABI
  fragments in src/chain/abi/ were fetched live from Blockscout, not hand-transcribed.
  Do NOT confuse with the V1 factory (0xA5aAb3F0c6EeadF30Ef1D3Eb997108E976351feB) —
  different contract, no bonding curve, a generic web search surfaces this by mistake.
- robinhoodchain.blockscout.com blocks bare curl (Cloudflare) but works fine with a
  normal browser User-Agent header — see BROWSER_UA in src/chain/holders.ts.
- KNOWN GAP, not fixed: the docs describe a "snipe tax" that decays from 99% to 0%
  over the first few seconds after launch (docs say 5s; PonsV2LaunchFactory.sol says
  15s by default, snapshotted per launch). PonsV2LaunchFactory.sol calls
  `curve.currentSnipeTaxBps()` / `curve.exemptFromSnipeTax()` at launch time, but a
  full read of PonsV2BondingCurve.sol (777 lines) found ZERO mentions of "snipe"
  anywhere — those functions are not in the public curve source, so calling them
  would fail against the real deployed contract. Deliberately NOT implemented in
  scanLaunch rather than shipping a call that's confirmed broken. If this matters for
  a later feature (it will, for anything timing a buy against the snipe-tax decay),
  fetch the live verified ABI per-curve from Blockscout
  (GET /api/v2/smart-contracts/{curve_address}) before trusting any quote math here —
  don't hardcode the docs' 5s figure.
- KNOWN GAP: holder concentration comes from Blockscout's /tokens/{address}/holders,
  which is PAGINATED — `topHolderShare` in the output is the top holder's share of the
  fetched page (default page size, first page only), not a verified figure across all
  holders. Good enough as a first-pass signal, mislabel it and someone will screenshot
  a wrong "50% concentration" claim as fact. Fix properly by paging through the whole
  holder list before shipping this as something the agent-judge feature quotes as a
  hard number.
- V2 launch creation is whitelist-gated per the docs ("Read this before integrating"
  box) and the protocol is explicitly unaudited (3rd-party audits in progress, none
  closed) — despite the gating, real launches ARE happening (411 TokenLaunched events
  observed in one ~13-minute sample window during this session), so there's no
  shortage of live data to test against, but `warden` should probably surface
  "protocol unaudited" as a standing disclosure somewhere in its own output eventually
  — not done yet, low priority.
