# Last updated: 2026-09-06 by session 8 (multi-launchpad: four.meme on BSC)

## What's done
- On-chain reader [0], repo fingerprint [1] — unchanged, passes:true.
- Judge [2], alerts/watch [3], execution gate [4] — unchanged, still blocked
  on credentials / on principle respectively (see sessions 5-7's notes).
- Multi-launchpad support [feature_list.json index: 5] — passes:true, fully
  verified, no credential blocker this time. Second adapter: **four.meme**
  on **BNB Smart Chain**, chosen deliberately (over Virtuals Protocol and
  Doppler, both considered and rejected as architecturally too different -
  auction-style / shared Uniswap-v4-hook rather than a per-token curve) for
  being genuinely structurally different from Pons in exactly the ways that
  stress-test whether the adapter interface actually generalizes rather than
  just being Pons with different addresses:
  - **LP-lock**: Pons has a dedicated vault contract (`isLocked`/
    `lockedTokenSupply`). four.meme has no locker at all - graduation burns
    ~100% of LP to the dead address via a real PancakeSwap V2 pair. Checking
    "is LP locked" means looking up that pair (factory `getPair(token,
    quote-or-WBNB)`) and reading ITS OWN `balanceOf(dead)+balanceOf(0)` over
    `totalSupply` - a completely different query shape, not a parameter
    change on the same query.
  - **Owner privilege**: Pons's deployer never has any privilege at any
    phase (a fixed protocol fact). four.meme's token `owner()` returns
    TokenManager2's own address WHILE the token is on the curve (confirmed
    live) and flips to `address(0)` at graduation - meaning "owner has
    privileges" is EXPECTED pre-graduation and only a red flag
    post-graduation. A naive port of Pons's "any owner privilege = bad"
    assumption would have false-positived on every single healthy,
    non-graduated four.meme launch. This is the concrete reason
    src/chain/launchpad.ts's `OwnerPrivilegeSignal` carries an
    `expectedRightNow` field instead of collapsing to one boolean.

  New modules: src/chain/{bscChain,bscClient,fourmeme}.ts, src/chain/abi/
  fourmeme.ts, src/chain/launchpad.ts (the common `LaunchpadScan` type both
  adapters normalize into). pons.ts gained its own `toLaunchpadScan`
  alongside fourmeme.ts's, so both produce the same shape.

  **Verification trail (research was delegated to an agent first, then
  every load-bearing fact was independently re-checked live in this
  session before being encoded - same two-step discipline as Pons):**
  - Re-verified `getTokenInfo`'s exact return tuple against 2 real live
    tokens myself before writing the ABI (matched the research report
    exactly: version, tokenManager, quote, ..., funds, maxFunds,
    liquidityAdded).
  - Re-verified `buyTokenAMAP` actually simulates successfully via a real
    `simulateContract` call against a live native-BNB-paired launch.
  - **Did NOT trust the research-reported WBNB address on sight** - called
    `name()`/`symbol()` on it myself before hardcoding it. It happened to be
    correct, but the point was verifying rather than assuming a well-known
    constant is right, exactly the lesson from Pons's snipe-tax discrepancy
    and the research agent's own wrong first guess at four.meme's proxy
    storage slot (they initially assumed the textbook EIP-1967 slot, got
    all-zeros back from a live `eth_getStorageAt`, and had to extract the
    real slot from the deployed bytecode instead - documented here so it
    isn't re-learned the hard way a third time).
  - Spot-checked the LP-burn arithmetic against a specific graduated pair
    (`0xf49d9C79A07922D3846C762c73b4df65205Ef772`) the research had already
    identified, reproducing its exact balances
    (totalSupply=59,396,969,616,568,150,296,050; dead=...295,050; zero=1,000
    - that 1,000 is Uniswap-v2-core's own `MINIMUM_LIQUIDITY` burn, not
    four.meme-specific) and confirming burnedFraction=1.0 → lpLocked=true.
  - **Could not self-discover a graduated four.meme launch** to test the LP
    path end-to-end from scratch: searching PancakeSwap's `PairCreated`
    events hit `-32005 limit exceeded` even at a 2000-block window - BSC's
    overall DEX volume (not just four.meme) is too high for this public
    RPC's log-query ceiling. Documented as an honest limitation rather than
    quietly working around it by, e.g., trying a paid indexer.
  - 12 new tests (6 fourmeme.ts + 1 cross-launchpad shape-diff test in
    launchpad.test.ts, all against live chain state), all passing. Full
    suite: 37 tests total, 35 passed + 2 failed in this session's run - see
    "External RPC issue hit this session" below before assuming those 2
    are a regression.

  **External RPC issue hit this session, unrelated to this work:**
  Robinhood Chain's public RPC (`eth_getLogs` specifically, not
  `eth_blockNumber`, which kept working at first) returned `"internal
  server errror"` (their typo) consistently, then on retry leaked an
  internal backend address in a timeout: `Post "http://10.31.45.18:8547/
  rpc": context deadline exceeded`. That's about as clear as external
  evidence gets that this was a real, live infrastructure problem on their
  RPC provider's side, not a bug introduced this session. It later cleared
  (a plain `eth_getLogs` call started returning real results again) - but
  by then this same session's own cumulative request volume (a full day of
  manual verification scripts plus repeated full test-suite runs against
  this one public endpoint) had separately triggered the already-documented
  429 rate limit (see session 6/7 notes), so re-running
  src/execute/buy.test.ts and src/watch/watch.test.ts back-to-back kept
  failing for a SECOND, different reason even after the first one resolved.
  Every piece of functionality these two tests cover was independently
  confirmed working via direct one-off scripts earlier in this same session
  (see the "Verification trail" above and session 7's notes) before the
  cumulative rate-limit set in - this is exhausted shared-resource capacity
  from testing itself, not a code defect. Don't chase this by adding more
  retries or backoff tuning; it clears on its own once request volume
  against this specific public RPC drops, which naturally happens once a
  session stops hammering it, not from a code change.
