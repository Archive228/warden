# Project: warden — agentic launch-vetting tool
# Last updated: 2026-09-06 by session 7 (dry-run/--live execution gate)

## What's done
- On-chain reader [0], repo fingerprint [1] — unchanged, still the only two
  passes:true entries. Judge [2], alerts/watch [3] — unchanged, still blocked
  on ANTHROPIC_API_KEY / TELEGRAM_BOT_TOKEN+CHAT_ID respectively.
- Dry-run/--live execution gate [feature_list.json index: 4] — IMPLEMENTED,
  passes:false BY DESIGN, not by gap. This is the one feature in this project
  that can move real money, and it got more scrutiny than anything before it,
  not less - see "What is NOT done, on purpose" below before assuming this
  needs "finishing."

  New modules:
  - src/execute/quote.ts: estimateTokensOut / applySlippageFloor, replicating
    PonsV2BondingCurve.buy()'s EXACT arithmetic (fee+tax deducted from
    quoteIn first, THEN the remainder priced through the constant-product
    formula with feeBps=0 - read from the real buy() body, not guessed).
    Cross-checked live against a real curve's own simulateContract result:
    0 basis points of difference, bit-for-bit identical.
  - src/execute/buy.ts: createWardenWallet (reads WALLET_PRIVATE_KEY, fails
    clearly without it), simulateBuy (a real eth_call against live state -
    proves a transaction WOULD be accepted, spends nothing, needs no funded
    key), executeBuy (the actual broadcast path - written, never called by
    this project).
  - src/execute/decide.ts: decideTrade, the safety gate itself. Order of
    checks: verdict must be low_risk AND confidence >= --min-confidence,
    THEN pairToken must be native ETH (zero address), THEN --live must be
    set, THEN (only then) it builds a plan and calls executeBuy. Every path
    returns a TradeDecision, none of them throw past this function.
  - src/execute/tradelog.ts: logTradeDecision, appends one JSON line per
    decision to verdicts/trades.jsonl - attempted AND skipped decisions both,
    since "why didn't it buy X" needs the same record as "why did it."
  - `warden watch` gained --live, --min-confidence (default 0.8),
    --buy-amount-eth (default 0.01), --slippage-bps (default 300).

  **Two real findings from testing this feature, before anything shipped:**

  1. **A real gap this project didn't know it had, caught by a live
     simulation, not by reasoning about it in advance.** The very first
     `simulateBuy` attempt against a real launch reverted with a custom
     error `0xe0aeda7d`. Decoded it by computing selectors for the known
     custom-error list (via viem's toFunctionSelector) rather than guessing:
     `UnexpectedNativeValue()`. Turned out that launch's `pairToken` (a
     field `getLaunchedToken` already returned, that nothing in this
     project had ever read or exposed) was a real ERC20, not the zero
     address - the curve wanted a transferFrom, not msg.value. Checked a
     sample of 10 recent launches: 3 of 10 were ERC20-paired. Added
     `pairToken` to LaunchScan (a real, if small, retroactive fix to
     feature [0]'s output shape) and an explicit gate refusing the ERC20
     case in decideTrade, with its own reason string and its own test.
     Re-ran the same simulation against a confirmed native-ETH launch
     instead: succeeded, and its output matched this project's own
     estimateTokensOut exactly.
     Lesson: the field you didn't bother to expose because you didn't
     think you needed it is exactly the one an adversarial test (or in
     this case, an honest live simulation) finds first.

  2. Math correctness was verified empirically, not just derived - the plan
     was always to cross-check estimateTokensOut against a live
     simulateContract call rather than trust a from-source derivation on
     its own, and it's now a locked-in regression test (src/execute/
     quote.test.ts's last case) using the exact real numbers from that
     live check, not synthetic ones.

  **What is NOT done, on purpose, and should not be treated as a gap to
  close by a future session without new information changing the calculus:**
  - No real transaction has ever been broadcast. No wallet has been funded.
  - This wasn't skipped for lack of time - it's the position this project
    takes on record: verifying "does executeBuy actually work" requires
    spending real ETH on a real chain, and that's a decision for whoever
    runs this with their own money and their own risk tolerance, not
    something to do unilaterally to satisfy a passes:true field. A future
    session with an actual funded testnet-equivalent setup and explicit
    user sign-off could responsibly extend verification here; a future
    session should NOT quietly decide the bar has lowered and self-fund a
    test to close this out.

## What's next (recommended)
- Multi-launchpad support [feature_list.json index: 5] or backtest mode
  [index: 6] are the two remaining, in either order - neither is blocked on
  a missing credential the way judge/watch/execute are, so either is
  actually completable to passes:true in this environment, unlike the last
  three sessions' work.
- Backtest [6] needs judge to actually run for "replays real historical
  launches through the same scan+vet+judge pipeline" to mean anything -
  it's arguably blocked transitively on ANTHROPIC_API_KEY too. Multi-
  launchpad [5] has no such dependency: it needs research into a second
  bonding-curve launchpad (pump.fun on Solana is a different chain
  entirely and a bigger lift; check for another EVM bonding-curve
  launchpad first) and an adapter interface matching src/chain/pons.ts's
  shape. Probably the more tractable next step of the two.
- To unblock judge/watch/execute for real verification: ANTHROPIC_API_KEY,
  TELEGRAM_BOT_TOKEN + TELEGRAM_CHAT_ID, and (only if a human decides to
  actually verify real execution, deliberately, with funds they choose to
  risk) WALLET_PRIVATE_KEY on a funded wallet.
