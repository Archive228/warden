  - src/alerts/telegram.ts: sendTelegramAlert, a single fetch() POST to Telegram's
    Bot API. Deliberately NOT a bot-framework dependency (node-telegram-bot-api was
    already removed once this project for pulling deprecated transitive deps for a
    feature that didn't exist yet - same logic applies here even harder, since
    warden never needs to RECEIVE Telegram updates, only send one message).
  - src/alerts/format.ts: formatVerdictMessage, a pure function, fully unit tested
    without needing any credential.
  - src/watch/watch.ts: findNewLaunchesSince (polls the factory for new
    TokenLaunched events since a given block) and watchLaunches (the poll loop:
    calls onLaunch per new token, catches and reports errors per-launch via
    onError instead of letting one bad launch kill an hours-long process).
  - `warden watch` wires it together: poll -> scanLaunch -> judgeLaunch(scan, null)
    -> saveVerdictLog -> sendTelegramAlert. `warden watch --once <token>` runs the
    same pipeline against one already-known launch immediately - this is the "test
    feed" feature_list.json's steps call for, so `watch` doesn't require waiting on
    a real new launch to test the wiring.

  **Two real bugs found live, both fixed, both worth internalizing:**

  1. **CLI arg-parsing bug.** `if (opts.once)` treats a falsy-but-provided value
     (an empty string) the same as "flag not given," so `watch --once ""` silently
     fell into the infinite poll loop instead of failing validation. Caught by
     accident: a curl call to find a fresh test token failed, fed an empty string
     through as `--once ""`, and the process had to be killed by hand rather than
     exiting on its own with a clear error - it looked like a hang, and for a few
     minutes genuinely was mistaken for one, before checking the actual output
     revealed it had been happily polling the whole time. Fixed to
     `opts.once !== undefined`. Now has a real regression test (src/cli.test.ts)
     that spawns the actual CLI as a subprocess with `--once ""` and asserts it
     exits 1 immediately rather than logging "watching for new launches."
     Lesson: `if (someOptionalString)` is almost never what you mean for a CLI
     flag - it conflates "not given" with "given an empty/falsy value," and the
     two should almost always be handled differently.

  2. **Confirmed, not just predicted: the public RPC rate-limits under sustained
     watch polling.** The same accidental long-running test (before it was killed)
     logged several clean "ANTHROPIC_API_KEY is not set" errors as real launches
     came in - proving the per-launch error isolation works exactly as designed -
     and THEN started logging "429 Too Many Requests" from
     rpc.mainnet.chain.robinhood.com on both eth_call and eth_blockNumber, even
     with the existing retry/backoff (3 retries, exponential) in scanLaunch. This
     was flagged as a predicted risk in session 3's notes ("the future watch
     feature will hit this harder") - now it's not a prediction, it's a reproduced
     fact. Response so far: bumped the default --poll-interval-ms from 15000 to
     30000 (cuts request volume, doesn't eliminate the ceiling), and documented in
     the README that real sustained use needs a paid RPC provider (Alchemy/
     QuickNode - the protocol's own docs recommend this for production regardless
     of warden). Did NOT attempt a deeper fix (a request queue/throttle across
     concurrent launch processing, or raising retry limits further) - diminishing
     returns against a free-tier rate limit that a paid RPC solves directly.

## What's next (recommended)
- Dry-run/--live execution gate [feature_list.json index: 4] is next in priority
  order. This is the one that touches a real wallet private key and can submit a
  real transaction with real money - treat it with more care than anything built
  so far, not less, even though the mechanics (an if-statement gating a
  sendTransaction call) are simple. Concretely:
  - Keep dry-run as the hard default; --live must be an explicit, unambiguous flag.
  - Do NOT test this by actually funding a wallet and submitting a real mainnet
    transaction. Verify the GATE (no tx without --live, no tx below
    --min-confidence, every attempted trade logged with the verdict that
    triggered it) with a wallet that has zero balance or on a path that never
    reaches the actual broadcast call - the point is to prove the safety logic is
    airtight, not to prove the trade itself works.
  - This project has caught real bugs by testing against live state every single
    feature so far (session 3's audit, session 4's contractAddress split, this
    session's two bugs) - the temptation to relax that discipline "just this once"
    because real execution is harder to safely test is exactly backwards; if
    anything this feature deserves MORE scrutiny before passes:true, not a pass on
    reduced verification because live-testing it responsibly is harder.
- To unblock judge/watch for real: add ANTHROPIC_API_KEY (and, for watch,
  TELEGRAM_BOT_TOKEN + TELEGRAM_CHAT_ID from @BotFather) to .env, then re-run and
  read the actual output before flipping either to true.
